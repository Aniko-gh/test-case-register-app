Test Case Register

This Test Case Register is a simple console application developed in Python for registering and listing test cases.

The application allows users to:
    - Create a test case
    - Display all registered test cases
    - Exit the application

Each test case contains:
    - A unique ID
    - Title
    - Description
    - Expected result

The application stores test cases in memory while it is running. No database or file storage is used.

Features:
- Create Test Case
    Users can create a new test case by providing:
        = Title
        = Description
        = Expected result
    The system validates that all mandatory fields have been filled in before the test case is created.

- List Test Cases
    Users can display all registered test cases.

If no test cases exist, the system will display an appropriate message.

Duplicate Detection:
The application prevents duplicate test cases from being registered by checking whether a test case with the same title already exists.

Automatic ID Generation:
Each registered test case receives a unique ID automatically generated by the repository.
Example: TC-001, TC-002, TC-003

Design Reflection

Relationship Between Design and Implementation

The implementation is based on the class diagram, activity diagram and sequence diagram created during the analysis and design phase.

The overall structure closely follows the UML design:
    - The user interacts with the system through the TestCaseDialog.
    - The dialog delegates business operations to TestCaseService.
    - The service performs validation and business rules.
    - The repository is responsible for storing and retrieving test cases.
    - The TestCase class represents the application's core domain object.

This separation of responsibilities follows the design documented in the UML diagrams.

Readability:
The program is divided into small classes with clearly defined responsibilities. This makes the code easier to understand because each class focuses on a single aspect of the system.

Maintainability:
Changes can be made in one layer without affecting the entire application.

Examples:
    - Validation rules can be modified in TestCaseService.
    - Storage behaviour can be modified in TestCaseRepository.
    - User interface changes can be made in TestCaseDialog.

This reduces coupling between different parts of the application.

Testability:
The separation between user interface, business logic and storage improves testability.

Most unit tests focus on:
    - Test case creation
    - Validation
    - Duplicate detection
    - Repository storage
    - Retrieval of test cases
    
Because the business logic is separated from the console interface, it can be tested independently using automated unit tests.

Design Changes:
The final implementation follows the original UML design closely, but several refinements were made during development to better reflect the final solution.

The original design used a record called CreateTestCase to transfer information when creating a test case. During implementation this was renamed to TestCaseRequest, which more clearly describes its role as a request object containing the data required to create a test case.

The repository design was also improved by introducing an internal nextId attribute. This change reflects the implementation where TestCaseRepository is responsible for generating unique test case identifiers such as TC-001, TC-002 and TC-003 when new test cases are registered.

Another addition was the promptMandatory() operation in TestCaseDialog. This operation represents the functionality that repeatedly prompts the user until a mandatory value is entered. Adding this operation to the diagram improved the alignment between the UML design and the implemented code.

The menu text and naming conventions were also updated. For example, the original diagrams used the names "Add Test Case" and "MAIN MENU", while the final implementation uses "Create Test Case" and "TEST CASE MANAGEMENT". These changes were made to improve consistency throughout the application and documentation.

Overall, the modifications did not change the system architecture or behaviour. Instead, they refined the design and ensured that the UML diagrams accurately represent the final implementation.
